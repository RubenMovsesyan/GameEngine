gpu::Device

Physical + logical Vulkan device, plus the NVRHI device wrapping it. Every GPU resource in the engine is loaned out from here.

Role

Picks a physical device (prefers discrete GPUs), creates the logical device with the features NVRHI requires, and wraps it in an nvrhi::IDevice (optionally through NVRHI's own validation layer). Exposes two loan functions — createBuffer/createTexture — that every other GPU-resource class (Mesh, Surface, LightManager) is built on top of.

Depends on / depended on by

Built from a gpu::Instance. Every class in graphics/ and scene/ that touches the GPU takes a const gpu::Device&.

Public API

struct DeviceConfig {
    VkSurfaceKHR present_surface = VK_NULL_HANDLE; // null => headless
    bool validation = true;
};

class Device {
    explicit Device(const Instance&, const DeviceConfig& = {});

    nvrhi::IDevice* nvrhi() const;
    nvrhi::vulkan::IDevice* vulkanDevice() const; // unwrapped, past the validation layer
    VkPhysicalDevice physical() const;
    VkDevice handle() const;
    VkQueue graphicsQueue() const;
    u32 graphicsQueueFamily() const;

    nvrhi::BufferHandle createBuffer(const nvrhi::BufferDesc&, const void* data = nullptr, usize data_size = 0) const;
    nvrhi::TextureHandle createTexture(const nvrhi::TextureDesc&, const void* data = nullptr, usize row_pitch = 0) const;
    std::unique_lock<std::recursive_mutex> lockSubmit() const;
};

Worth knowing

  • createBuffer/createTexture upload synchronously when given data — open a throwaway command list, write, submit, wait. Fine for one-off asset loads; calling either mid-frame while another command list is already open triggers NVRHI's "two immediate command lists open at once" validation error (this bit LightManager once — see its explicit build() step — and InstancedMesh's instance-buffer upload, see Renderer).
  • m_submit_mutex (a std::recursive_mutex) guards both functions' entire bodies, and lockSubmit() lets a caller hold that same lock across a wider span. Added once Texture could load on a detached background thread. A mutex around createBuffer/createTexture alone only stops two threads calling those two functions at the same time — it does nothing about a background createTexture() landing while Renderer's own long-lived m_cmd is open for an entire frame (opened in beginFrame(), not closed until endFrame()), since that command list is never created through Device at all. Confirmed by testing: with only the per-call mutex, smile_cube.gltf (which triggers a background texture load) hit "two immediate command lists open at once" intermittently — a genuine timing race, not a same-thread ordering bug like the LightManager/InstancedMesh cases above. Fix: Renderer::beginFrame() calls lockSubmit() and holds the returned lock in a member until endFrame() releases it, so the whole frame is inside the same critical section as any background createBuffer/createTexture call. The mutex is recursive specifically so Renderer can still call into createBuffer/createTexture itself (directly, or via something like InstancedMesh::uploadIfDirty()) while already holding the frame lock, without self-deadlocking.
  • Requires Vulkan 1.3 dynamic rendering + synchronization2, and 1.2 timeline semaphores — NVRHI's hard requirements, not optional.
  • vulkanDevice() exists specifically because the swapchain's binary acquire/present semaphores need to be staged onto a submission below the validation layer's abstraction.
