graphics::Skybox

A plain value type describing what fills the pixels no geometry covered — today a procedural vertical gradient, with a variant slot already reserved for a cubemap.

Role

Handed directly to Renderer::setSkybox() by the render loop (scene::Scene, which used to carry one, no longer exists). Skybox itself holds no GPU resources for the gradient case — it's three colours and a scalar. The Renderer unpacks it into push constants for a dedicated full-screen sky pass that runs after lighting and before post-process.

Depends on / depended on by

Depends only on Eigen and (for the future CubemapSky slot) Texture. Consumed by graphics::Renderer. The render loop (sandbox/model_test/main.cpp) constructs one and calls renderer.setSkybox(scene.skybox()).

Public API

// Procedural vertical gradient: ground colour at the horizon fading to zenith overhead.
// zenith/ground are linear radiance in the lights' units, calibrated for the default exposure.
struct GradientSky {
    Eigen::Vector3f zenith{90.0f, 120.0f, 170.0f}; // slightly unsaturated skyblue
    Eigen::Vector3f ground{25.0f, 25.0f, 25.0f};   // dim ground bounce
};

// Reserves the variant slot; no cubemap loader exists yet.
struct CubemapSky {
    Texture cubemap;
};

struct Skybox {
    std::variant<GradientSky, CubemapSky> source = GradientSky{};
    f32 intensity = 1.0f;
};

Worth knowing

  • Why a dedicated pass and not a branch in lighting.frag. A cubemap needs its own samplerCube binding. Keeping the sky in a separate pass with its own binding layout means adding the cubemap later touches only m_sky_binding_layout and sky.frag — never the shared 6-slot lighting layout, and no lighting.frag recompile. The gradient pass and the eventual cubemap pass are the same pass with a different fragment shader; sky.frag already switches on a kind push constant (0 = gradient, 1 = cubemap) with the cubemap case stubbed out.
  • variant, not an enum with dead fields. A gradient and a cubemap are mutually exclusive, so the two configs live in separate structs in a std::variant (matching ModelPart::mesh). intensity sits outside the variant because it applies to both — a plain artistic multiplier on top of the calibrated sky colour.
  • The gradient colours are linear radiance in the lights' units. The lighting output is HDR and gets an ACES + exposure tonemap at roughly 0.003 (see Renderer), so the sky is authored in that same scene-referred range: zenith (90, 120, 170), ground (25, 25, 25) land mid-curve after exposure. The default Skybox{} with intensity = 1.0 renders a plausible sky with no per-scene tuning; reach for intensity only when you want a deliberately brighter or dimmer sky.
  • The gradient band is tight and just above the horizon. sky.frag does mix(ground, zenith, smoothstep(-0.05, 0.25, dir.y)) on the world-space view-ray Y — so everything below the horizon is flat ground colour, the fade happens in a wedge above it, and the upper sky dome is flat zenith colour. Widen the smoothstep edges further for a softer, taller gradient.
  • Constructing a CubemapSky today sets kind = 1 but renders nothing new. Renderer::setSkybox() recognises the alternative and flips the kind, but the samplerCube binding isn't wired and the gradient stash is left untouched, so the pass still draws the last gradient. Finishing cubemaps means: cubemap support in Texture (VK_IMAGE_VIEW_TYPE_CUBE, 6 layers, a 6-face / equirect-HDR loader), a samplerCube at binding 2 of m_sky_binding_layout, and un-commenting the case 1: in sky.frag.
  • The Renderer's ambient default was tuned to match this. lighting.frag's flat ambient term (a stand-in for sky bounce until IBL exists) defaults to (300, 300, 300) — large for the same exposure reason, but still a hand-tuned stand-in and not derived from the sky gradient. The two are unrelated today; IBL later unifies them.
