Synchronization

The subtlest part of the engine, and the part the previous attempt got wrong in three separate ways. Two objects matter: FrameRing and Swapchain. The question that governs both is what is each synchronization object indexed by.

What is indexed by what

There are two independent counts in flight and they are not the same number. Frames in flight is a CPU throttle we choose — it defaults to 2. Swapchain image count is whatever the driver gives us — typically 3. Confusing the two is the classic Vulkan sync bug.

ObjectIndexed byLives inWhy
command buffer frame slot FrameRing One recording per in-flight frame.
in-flight fence frame slot FrameRing The CPU throttle. One per in-flight frame by definition.
acquire semaphore frame slot FrameRing Must exist before the image index is known — you pass it to acquireNextImage.
render-finished semaphore swapchain image Swapchain Nothing on the CPU reports when a present is done waiting on it. See below.
The structural trick

Each object physically lives in the class that owns the thing it is indexed by. You cannot accidentally index the render-finished semaphore by frame slot, because FrameRing doesn't have one — Swapchain::renderFinished(image_index) is the only way to get it. Mixing them up is a compile error rather than a convention someone has to remember.

ShaderPlayground indexed command buffers by image_index in its renderer and by frame_index in its compute dispatcher — the same array meaning two different things in two files.

Why acquire is per-frame but render-finished is per-image

These pull in opposite directions and the reasoning is different for each.

Acquire must be per-frame-slot, and per-image isn't even constructible: you have to hand a semaphore to vkAcquireNextImageKHR before it tells you which image you got. Reuse is provably safe anyway, because FrameRing::begin() waits on that slot's fence, and that fence is signalled by the very submit that waited on that semaphore. By the time the slot comes around again, the semaphore is guaranteed unsignalled and wait-free.

Render-finished must be per-image, because there is no CPU-side signal for "the present engine has finished waiting on this semaphore" — no fence, no callback. The only ordering guarantee Vulkan gives you is that you cannot reacquire image i until its previous present is done with it. So sizing that array by image count and indexing it by image_index is what makes reuse safe. Get it wrong and the validation layer flags it under VUID-vkQueuePresentKHR-pWaitSemaphores.

FrameRing

FrameRing holds N slots of {command buffer, fence, semaphore}. It knows nothing about swapchains or rendering, which is exactly what lets a compute or physics loop use it unchanged. It is the only frames-in-flight bookkeeping in the engine. 

class FrameRing {
public:
    struct Frame {
        const vk::raii::CommandBuffer& cmd;
        vk::Semaphore semaphore;
        vk::Fence fence;
    };

    FrameRing(const Device&, u32 queue_family, u32 frames_in_flight = 2);

    // Waits on this slot's fence and resets its command buffer. Deliberately does not
    // reset the fence: submit() does, so bailing out after begin() is safe.
    Frame begin() const;

    void advance() { m_slot = (m_slot + 1) % m_cmds.size(); }
};

Fences are created already signalled, so the very first begin() doesn't block:

m_fences.emplace_back(*device, vk::FenceCreateInfo{.flags = vk::FenceCreateFlagBits::eSignaled});

What actually overlaps

With 2 frame slots and 3 swapchain images, slots alternate 0,1,0,1,… while images cycle 0,1,2,0,…. They drift against each other, which is precisely why the two arrays cannot share an index. The CPU also runs ahead: it is recording frame n+1 while the GPU is still executing frame n.

The fence reset, and the deadlock it avoids

The obvious place to reset an in-flight fence is right after waiting on it, inside begin(). That is a trap.

The bug

Wait on the fence and reset it in begin(). Then acquireNextImage returns VK_ERROR_OUT_OF_DATE_KHR — a window resize — so you return early without submitting. The fence is now unsignalled, and nothing will ever signal it, because the submit that would have done so never happened. Next time this slot comes around, waitForFences blocks forever.

The fix needs no extra API. begin() waits but does not reset; submit() resets, immediately before vkQueueSubmit2: 

FrameRing::Frame FrameRing::begin() const {
    // Deliberately no resetFences here: submit() does it, so bailing out is safe.
    while (m_device->waitForFences(*m_fences[m_slot], vk::True, UINT64_MAX) == vk::Result::eTimeout) {
    }
    m_cmds[m_slot].reset();
    return {m_cmds[m_slot], *m_semaphores[m_slot], *m_fences[m_slot]};
}
void submit(const Device& device, const vk::raii::Queue& queue, const SubmitInfo& info) {
    // ...
    if (info.fence) {
        device->resetFences(info.fence);
    }
    queue.submit2(/* ... */, info.fence);
}

Bailing out anywhere between begin() and submit() now leaves the fence signalled, so the slot stays usable. advance() is likewise called only after a successful submit, so a skipped frame reuses the same slot rather than burning one.

Swapchain

Swapchain takes a bare vk::SurfaceKHR, so it never learns what a window is. It owns the swapchain, the image views, and one render-finished semaphore per image.

Out-of-date and suboptimal are not errors

Both are normal, every-resize control flow. They are return values here and never escape the class: 

struct Acquired {
    u32 image_index = 0;
    bool ok = false;   // false => out of date, recreate and skip the frame
};

[[nodiscard]] Acquired acquire(vk::Semaphore signal);
[[nodiscard]] bool present(const vk::raii::Queue&, u32 image_index);

ShaderPlayground threw std::runtime_error for both, routing every window resize through the exception mechanism with a string the caller had to match on.

Suboptimal is treated as success — deliberately

Swapchain::Acquired Swapchain::acquire(vk::Semaphore signal) {
    try {
        const auto [result, index] = m_swapchain.acquireNextImage(UINT64_MAX, signal, nullptr);
        // eSuboptimalKHR: index is valid and the semaphore IS signalled, so render it.
        // Skipping would strand a signalled semaphore; present() asks for the rebuild.
        return {index, result == vk::Result::eSuccess || result == vk::Result::eSuboptimalKHR};
    } catch (const vk::OutOfDateKHRError&) {
        return {0, false}; // semaphore was not signalled on this path
    }
}

This asymmetry is the important detail. On eSuboptimalKHR the acquire succeeded: the image index is valid and the semaphore has been signalled. Skipping the frame would leave a signalled semaphore with nothing waiting on it — and the next use of that slot would then wait on an already-signalled semaphore, desynchronising the ring. So the frame is rendered normally, and present() reports the suboptimal result to trigger a rebuild before the next frame.

On VK_ERROR_OUT_OF_DATE_KHR the semaphore is guaranteed not signalled, so bailing out is safe. That is the only path that skips.

Why not VULKAN_HPP_NO_EXCEPTIONS?

Because it is a global switch that converts every vk::raii call in the whole codebase into ResultValue unwrapping, in exchange for deleting two catch blocks that live in one file and are invisible to callers. vk::OutOfDateKHRError is a purpose-built exception type, and catching it exactly where it is expected is the intended use.

Rebuilding

build() handles both construction and recreation. The ordering inside it matters in two places: 

// Views and semaphores must die before the swapchain they came from.
m_views.clear();
m_render_finished.clear();

m_swapchain = vk::raii::SwapchainKHR{
    **m_device,
    vk::SwapchainCreateInfoKHR{
        // ...
        .presentMode  = vk::PresentModeKHR::eFifo, // always supported, no tearing
        .oldSwapchain = *m_swapchain,
    },
};

Passing the live swapchain as oldSwapchain lets the driver reuse its resources; the move-assignment is what destroys the old one, and it happens only after the new one exists. Semaphores are rebuilt here too, one per image, since the image count can change.

Extent selection defers to the surface unless the surface defers to us:

// UINT32_MAX means the surface defers to us; otherwise its extent wins.
m_extent = caps.currentExtent.width == UINT32_MAX
    ? vk::Extent2D{std::clamp(want.width,  caps.minImageExtent.width,  caps.maxImageExtent.width),
                   std::clamp(want.height, caps.minImageExtent.height, caps.maxImageExtent.height)}
    : caps.currentExtent;

Resize, end to end

The renderer drives it, and the sequence is short:

if (m_needs_recreate || extent != m_swapchain.extent()) {
    m_device->waitIdle();
    m_swapchain.recreate(extent);
    m_needs_recreate = false;
}

m_needs_recreate is set from either direction — a failed acquire or a non-eSuccess present — and the extent comparison catches the case where the window changed size without either reporting it.

waitIdle() is a blunt instrument: it stalls the whole device rather than tracking which frames still reference the old swapchain. That is a deliberate simplification. The fine-grained version only matters if resize stutter is ever measurable.

Minimised windows

A minimised window reports a zero extent, and creating a swapchain with one is invalid. drawFrame returns immediately, and the caller blocks in glfwWaitEvents rather than spinning a busy loop.
