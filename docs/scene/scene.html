scene::Scene

Models grouped with the Lights that illuminate them — what a loaded glTF file (or a hand-built level, later) amounts to.

Role

Owns its Models and Lights by value (same way Model owns its Meshes). render() loops its models, sharing one caller-supplied world transform across all of them — no per-model placement exists yet, since nothing has asked for it.

Depends on / depended on by

Depends on scene::Model, graphics::Light/Renderer/Camera. Built by scene::loadGltf; consumed directly by test/game code (sandbox/model_test/main.cpp calls .render() and .lights()).

Public API

class Scene {
    void addModel(Model model);
    void addLight(graphics::Light light);

    void render(graphics::Renderer&, const Eigen::Matrix4f& world_transform, const graphics::Camera&);
    const std::vector<graphics::Light>& lights() const;
    std::vector<Model>& mutableModels();

    std::string display() const;   // implements utils::Display
};

Worth knowing

  • This is a narrower, concrete thing than "a registry of everything in a running game" — that's a separate, still-undecided future idea (non-owning references, add/remove by handle). Scene here is the direct, necessary consequence of Model no longer having anywhere to put lights parsed out of a glTF file, not a first cut at that bigger registry.
  • render() is non-const, cascading from Model::render() needing mutable access so an InstancedMesh part can upload its dirty instance buffer during render.
  • mutableModels() exists so callers can reach into a loaded Scene's Models/ModelParts after the fact — e.g. converting parts to InstancedMesh and populating instances post-load, which sandbox/model_test/main.cpp does. No const overload, matching how Model::mutableParts() is also mutable-only.
  • display() lists model part-counts and light types — see Display.
