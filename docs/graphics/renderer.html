graphics::Renderer

A deferred renderer driving its own swapchain-present loop, meant to run off a worker thread.

Role

Three passes per frame: a geometry (G-buffer) pass per mesh, one full-screen lighting pass, then a post-process chain that narrows HDR down to the display. Owns every GPU pipeline/texture involved; callers only ever call the four methods below.

Depends on / depended on by

Depends on gpu::Device/gpu::Swapchain, and on Mesh, Camera, LightManager, PostProcessChain, Surface. Driven directly by whatever code owns the render loop (currently sandbox/model_test/main.cpp, via a worker thread started by app::Application).

One frame

Worth knowing

  • Lighting no longer writes the swapchain directly. It writes an RGBA16_FLOAT offscreen target (m_hdr_color) so light values can exceed 1.0 without hard-clipping — real Blender-exported intensities are physically large (see Light), and an 8-bit LDR target clips anything over 1.0 straight to white. PostProcessChain's last pass is what actually narrows HDR to the display.
  • Point-light shading needs per-fragment world position, which the lighting pass doesn't have directly. Rather than adding a 4th G-buffer target for it, the lighting shader reconstructs it from the existing depth buffer: sample depth, build NDC, multiply by the inverse view-projection matrix, divide by w. That matrix comes straight from Camera's own cache (inverseViewProjectionMatrix()) — Renderer doesn't compute any matrix inverse itself. This keeps the geometry pass writing exactly what it always did.
  • NDC.y is negated in reconstructWorldPosition (lighting.frag): -(uv.y * 2.0 - 1.0), not the plain uv.y * 2.0 - 1.0 every other NDC component uses. NVRHI's Vulkan backend flips Y at the viewport level for every draw (VKViewportWithDXCoords in vulkan-graphics.cpp, the standard negative-height viewport trick), completely separate from anything the projection matrix does. Rasterizing and sampling the G-buffer both go through that same viewport convention automatically, so they stay self-consistent without anyone thinking about it — but reconstructWorldPosition is pure math bypassing the viewport entirely, so it has to undo that flip by hand. Symptom when this was missing: point-light shading on a perfectly static object visibly shifted as the camera moved vertically (light appeared to move opposite the camera on Y only, since the viewport's flip is Y-only) — a real bug, not a hypothetical one.
  • renderMesh()/setLights() stash camera/light state for endFrame() to read later — correct only when called once per frame with one camera, which is the only way this engine calls them today.
  • NVRHI's Vulkan backend offsets sampler bindings by 128 by default; every binding layout here zeroes it explicitly (VulkanBindingOffsets().setSamplerOffset(0)) so shader source can use plain binding = N numbers.
  • gbuffer_state.rasterState.setFrontCounterClockwise(true) matches Camera's projection having no Y-flip — see Camera's note on why these two settings are a matched pair.
  • No frames-in-flight pacing — vkDeviceWaitIdle after every submit. Simple and correct; revisit if/when frame pacing actually matters for performance.
