graphics::Skybox

A plain value type describing what fills the pixels no geometry covered — today a procedural vertical gradient, with a variant slot already reserved for a cubemap.

Role

Carried by Scene (one per scene), handed to Renderer::setSkybox() each frame the same way lights are. Skybox itself holds no GPU resources for the gradient case — it's three colours and a scalar. The Renderer unpacks it into push constants for a dedicated full-screen sky pass that runs after lighting and before post-process.

Depends on / depended on by

Depends only on Eigen and (for the future CubemapSky slot) Texture. Held by scene::Scene; consumed by graphics::Renderer. The render loop (sandbox/model_test/main.cpp) constructs one and calls renderer.setSkybox(scene.skybox()).

Public API

// Procedural vertical gradient: ground colour at the horizon fading to zenith overhead.
struct GradientSky {
    Eigen::Vector3f zenith{0.53f, 0.71f, 1.0f}; // skyblue
    Eigen::Vector3f ground{0.15f, 0.15f, 0.15f}; // dark gray
};

// Reserves the variant slot; no cubemap loader exists yet.
struct CubemapSky {
    Texture cubemap;
};

struct Skybox {
    std::variant<GradientSky, CubemapSky> source = GradientSky{};
    f32 intensity = 1.0f;
};

Worth knowing

  • Why a dedicated pass and not a branch in lighting.frag. A cubemap needs its own samplerCube binding. Keeping the sky in a separate pass with its own binding layout means adding the cubemap later touches only m_sky_binding_layout and sky.frag — never the shared 6-slot lighting layout, and no lighting.frag recompile. The gradient pass and the eventual cubemap pass are the same pass with a different fragment shader; sky.frag already switches on a kind push constant (0 = gradient, 1 = cubemap) with the cubemap case stubbed out.
  • variant, not an enum with dead fields. A gradient and a cubemap are mutually exclusive, so the two configs live in separate structs in a std::variant (matching ModelPart::mesh). intensity sits outside the variant because it applies to both — it scales the sky colour before the tonemap.
  • intensity is a calibration knob, and the default is nowhere near calibrated. The lighting output is HDR and gets an ACES + exposure tonemap at roughly 0.003 (see Renderer). A literal (0.53, 0.71, 1.0) sky colour is crushed to near-black by that exposure, so intensity has to lift it back — sandbox/model_test/main.cpp currently sets 300.0f as a first guess. sky.frag carries a FIXME that the gradient still needs proper calibration against the exposure. Expect to tune intensity per scene, like a light's intensity.
  • The gradient band is tight and just above the horizon. sky.frag does mix(ground, zenith, smoothstep(-0.02, 0.12, dir.y)) on the world-space view-ray Y — so everything below the horizon is flat ground colour, the fade happens in a narrow wedge just above it, and most of the visible sky dome is flat zenith colour. Widen the smoothstep edges if you want a softer, taller gradient.
  • Constructing a CubemapSky today sets kind = 1 but renders nothing new. Renderer::setSkybox() recognises the alternative and flips the kind, but the samplerCube binding isn't wired and the gradient stash is left untouched, so the pass still draws the last gradient. Finishing cubemaps means: cubemap support in Texture (VK_IMAGE_VIEW_TYPE_CUBE, 6 layers, a 6-face / equirect-HDR loader), a samplerCube at binding 2 of m_sky_binding_layout, and un-commenting the case 1: in sky.frag.
  • The Renderer's ambient default was tuned to match this. lighting.frag's flat ambient term (a stand-in for sky bounce until IBL exists) defaults to (300, 300, 300) — the same order of magnitude as the gradient's intensity, for the same exposure reason. Tune the two together.
