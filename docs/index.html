System Overview

A game engine built as independent modules. Each module is a top-level directory that compiles to its own static library. Read this page first — it explains how the pieces relate before you dive into either module.

The central idea

The engine separates talking to the GPU from rendering. That split exists so the GPU can later drive physics and general-purpose compute without those subsystems depending on the renderer.

This is the second attempt at that split. The first one — ShaderPlayground — declared it and never built it, in ways worth naming because every rule below is a direct reaction to one of them:

What went wrong thereWhat this repo does instead
Pipeline — a rendering concept — was defined inside gpu_core.hpp, so the "GPU core" ended up including shaderc and <GLFW/glfw3.h>. 324 of 1049 lines in the GPU layer were pipeline and descriptor code. gpu/ contains no rendering concepts at all, and a grep gate proves it never sees GLFW.
GpuQueue, GpuGraphicsQueue, GpuComputeQueue were forward-declared and friended but never defined. The whole queue API was two public uint32_t family indices. No queue wrapper is written, because vk::raii::Queue already is one. Device hands them out directly.
GpuCore had 11 friend declarations, so its private section was effectively public and its one accessor was bypassed everywhere. Zero friend declarations. Device::operator* returns the vk::raii::Device, so there is nothing left to bypass.
Renderer and compute duplicated command pools, command buffers, fences, semaphores and frame-index bookkeeping — seven near-verbatim pairs. One gpu::FrameRing and one gpu::submit, used by both.
Inheritance ran three deep. handle_resize was pure virtual, both implementations were empty, and nothing ever called it. No virtual functions in either module. Composition only.
Compute↔graphics semaphore sync was declared in the API and commented out in the implementation. Nothing to comment out: compute would use the same submit path graphics already exercises every frame.
The rule that makes it real

gpu/ never includes GLFW and never mentions graphics/. That is not a convention anyone has to remember — it is checked mechanically, and the check is in AGENTS.md: 

grep -rn 'GLFW\|glfw\|graphics/' gpu/     # only the comment in gpu/vk.hpp
nm -uC .build/libgpu.a | grep -i glfw     # empty

As long as those stay clean, a future physics/ can link libgpu.a without dragging in a window or a renderer.

Layout inside a module

<module>/include/<module>/   public API — the only headers other modules may include
<module>/src/                implementation and private headers
<module>/docs/               how this module works (an HTML page, dark mode)

Only include/ goes on another module's include path, so the public boundary is enforced by the build script rather than by discipline.

Build system

There is no CMake. build.c is a C23 program that includes buildcpp/build.h and describes the build directly. 

clang -std=c23 build.c -o build   # once, to bootstrap
./build                           # every time after

./build rebuilds itself when build.c or buildcpp/build.h changes, then re-runs. It also writes compile_commands.json for clangd. Artifacts land in .build/.

Steps

A build step is one compiler invocation set plus one output. Steps run in order, so dependencies come first. Each step needs its own compiler and flags — nothing is inherited — which is why build.c funnels the shared ones through one helper: 

// Applied to every step, so these can never drift between them.
static void cxxStep(Build* build) {
    buildStepSetCompiler(build, (char*)CXX);
    buildAddCompilationFlag(build, (char*)CXX_STD);
    buildAddCompilationFlag(build, "-DVULKAN_HPP_NO_CONSTRUCTORS");
    buildAddCompilationFlag(build, "-DVMA_STATIC_VULKAN_FUNCTIONS=0");
    buildAddCompilationFlag(build, "-DVMA_DYNAMIC_VULKAN_FUNCTIONS=1");
    buildAddInclude(build, newDirectInclude("gpu/include"));
    buildAddInclude(build, newDirectInclude("common"));
}
Why that helper matters

-DVULKAN_HPP_NO_CONSTRUCTORS changes the definition of every vk:: struct — it strips their constructors so designated initializers work. If one step had it and another didn't, the same struct would have two different definitions across translation units: a silent ODR violation. Setting it in one place that all three steps call makes a mismatch impossible.

Gotchas worth knowing before you edit build.c

RuleWhy
Every source file needs an explicit buildAddObject. There is no globbing. Adding a .cpp means adding a line.
A step's output must not share a name with a top-level source directory. Object files mirror source paths into .build/, so sandbox/src/main.cpp makes .build/sandbox a directory — hence the executable is sandbox_app.
Use newBuild, never newBuildWithCompiler. The build script recompiles itself with the default compiler using -std=c23. Point that at clang++ and the self-rebuild breaks. Set clang++ per step instead.
Link graphics before gpu. ar archives carry no dependency information and ld resolves them left to right, so dependents must precede their dependencies.
libfoo.a outputs are archived with ar rcs, not linked. A patch to buildcpp detects the .a suffix. Archives take no link flags, so consumers declare their own links.

System dependencies

sudo pacman -S vulkan-headers vulkan-validation-layers vulkan-memory-allocator glfw

All install into /usr/include, so no extra include paths are needed. Note that vulkan-icd-loader alone is not enough — that ships only libvulkan.so, with no headers.

Adding a module

  1. Create <module>/include/<module>/, <module>/src/ and <module>/docs/.
  2. Add a build step in build.c before its dependents, calling cxxStep(build), then its own buildAddInclude, its objects, and buildStepSetOutput(build, "lib<module>.a").
  3. Add buildAddInclude(build, newDirectInclude("<module>/include")) to every step that consumes it.
  4. Add buildAddLink(build, newPathLinkWithDep("<module>", BUILD_DIR)) to the executable step, positioned before the modules it depends on.
  5. Write <module>/docs/index.html, linking ../../docs/style.css.

A module that wants the GPU links gpu/ and nothing else. It must not link graphics/ unless it genuinely needs a window.

Current state

The engine opens a window and draws one hardcoded triangle over an animated clear colour. The milestone after proving the gpu/graphics seam was proving the pipeline/shader path end to end, still with the least amount of machinery that does that honestly.

What is verified today:

  • Validation layers enabled and confirmed live by a positive control — deleting the final image barrier makes the layer fire immediately through rlog.
  • Clean exit with zero object-leak reports at vkDestroyInstance, which is the proof that destruction ordering is right.
  • ~1800 frames sustained with no validation output, so the frame ring wraps hundreds of times without a semaphore-reuse violation.
  • VMA exercised by a real host-visible allocation with write and readback.
  • A dynamic-rendering graphics pipeline draws a shader-hardcoded triangle with interpolated vertex colours — no vertex buffer yet, see graphics/'s notes.

Deliberately not built yet, and not scaffolded for:

vertex buffers descriptor sets staging buffers async compute depth buffer MSAA present-mode choice

QueueFamilies::transfer is selected but unused. Selecting it costs two lines now; changing the struct's shape later would touch every construction site.
