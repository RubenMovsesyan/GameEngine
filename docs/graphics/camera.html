graphics::Camera

View + projection matrices, Vulkan-convention, hand-derived (no glm/GLU dependency).

Role

A camera with an explicit position and a direction it points in, a fixed world-up of (0,1,0), and a perspective projection built directly from FOV/aspect/near/far. No scene-graph attachment, no controller logic — mutablePosition()/mutableDirection() exist so calling code (e.g. WASD movement + mouse-look in a test harness) can drive it directly. Every matrix (view, view-projection, and their inverses) is cached and only rebuilt when something actually marks the camera dirty.

Depends on / depended on by

Depends only on Eigen. graphics::Renderer::renderMesh() reads viewProjectionMatrix()/inverseViewProjectionMatrix()/position() every call; scene::Model/scene::Scene::render() just forward a const Camera& through.

Public API

class Camera {
    Camera(f32 fov_y_radians, f32 aspect_ratio, f32 near_plane, f32 far_plane,
           const Eigen::Vector3f& position, const Eigen::Vector3f& direction, const Eigen::Vector3f& up);

    const Eigen::Matrix4f& transformationMatrix() const;       // world -> camera space
    const Eigen::Matrix4f& viewProjectionMatrix() const;        // projection * transformationMatrix()
    const Eigen::Matrix4f& inverseViewProjectionMatrix() const; // for reconstructing world position from depth
    const Eigen::Vector3f& position() const;
    const Eigen::Vector3f& direction() const;

    Eigen::Vector3f* mutablePosition();   // for driving it in place; unconditionally marks dirty
    Eigen::Vector3f* mutableDirection();  // same
};

Direction, not a look-at target

Earlier this stored a target point and derived forward = target - position every rebuild — which meant moving the camera changed where it looked unless the caller also re-issued a matching setLookAt() every frame, just to hold direction steady. Storing direction directly instead means position and orientation are fully independent: WASD movement never touches direction, mouse-look never touches position, and neither needs to know about the other. There's no setLookAt() anymore — orient the camera by writing through mutableDirection() directly (e.g. from yaw/pitch, see InputState's mouse delta).

Caching

m_projection/m_inverse_projection are built once, in the constructor — nothing in this class can change fov/aspect/near/far after construction, so there's nothing to invalidate them. m_view/m_view_inverse/ m_view_projection/m_inverse_view_projection rebuild lazily, on the next accessor call after mutablePosition() or mutableDirection() was called — both mark a m_dirty flag unconditionally on every call, even if the caller doesn't end up writing a different value through the returned pointer, since the class has no way to know afterward whether anything actually changed. A frame that never touches either pointer costs nothing beyond the flag check.

The rebuilt inverse view-projection is not a generic 4x4 matrix inverse — both factors it's built from have cheap closed forms:

  • m_view is a rigid transform (rotation + translation, no scale). Its inverse is just the rotation block transposed (free — the same right/up/forward vectors are already on hand) with the original, pre-transform camera position restored as the translation column.
  • m_projection is sparse (5 nonzero entries); its inverse has a 5-entry closed form too, computed once in the constructor alongside the forward matrix.
  • inverse_view_projection = view_inverse * inverse_projection — one 4x4 multiply of two already-cheap matrices, not an inverse of their product.

Worth knowing

  • Projection has no Y-flip (m_projection(1,1) = f, not -f). Vulkan clip space is Y-down by default, and the textbook advice for porting an OpenGL-style projection to Vulkan is to negate that term — but this pipeline's view matrix already produces the correct on-screen orientation without one. Adding the textbook flip mirrors the image (confirmed empirically: it also inverted every mesh's apparent winding, i.e. rendered everything inside out). If you ever "fix" an upside-down render by flipping this sign back, you must also flip graphics::Renderer's gbuffer RasterState.frontCounterClockwise to match, or culling breaks instead. The two settings are a matched pair, not independent — a Y-flip mirrors the transform, which necessarily inverts screen-space winding parity too.
  • Depth range is Vulkan's [0,1], not OpenGL's [-1,1] — the row-2 near/far terms are derived for that directly, not adapted from a GL formula.
  • transformationMatrix() is a standard right-handed look-at (right = forward × up, up' = right × forward), camera looking down -Z in view space — matches glTF's own camera convention, which matters since scene::loadGltf loads content authored under that convention.
