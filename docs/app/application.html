app::Application<S> and app::Context

Owns the window, the sokol_gfx context, the frame loop, and the app’s State S — for exactly as long as the GPU is up.

Role

An app is a State type: whatever the app needs between frames (renderers, the presenter, a camera, settings). Application<S> builds it once the GPU is up, calls S::frame every frame, and destroys it before the GPU goes down. The State’s constructor is the app’s init and its destructor is the app’s cleanup, so members that hold GPU handles are plain members. 

run(): window opens → sg_setup() → S(context) → workers start
       → S::frame(context) every frame
       → workers stop + join → ~S() → sg_shutdown() → run() returns

The AppState concept

template <typename S>
concept AppState = std::constructible_from<S, Context&> && !std::convertible_to<Context&, S> &&
                   requires(S& state, Context& context) {
                       { state.frame(context) } -> std::same_as<void>;
                   };
  • explicit S(Context&) — the constructor must be explicit; the !convertible_to clause rejects an implicit one.
  • void frame(Context&) — runs on the render thread, once per frame.
  • ~S() — not in the concept, but it is the cleanup: by then every worker has been joined and sokol is still up.

Example

struct ElectronCloud {
    graphics::renderers::ClearRenderer renderer{kYellow};
    graphics::Presenter presenter;

    explicit ElectronCloud(app::Context&) {}
    void frame(app::Context&) { presenter.present(renderer); }
};

int main(int argc, char** argv) {
    app::Application<ElectronCloud> app{{.title = "ElectronCloud"}, argc, argv};
    app.run();
}

Settings from the command line are read by the State itself, in its constructor: 

Sandbox::Sandbox(app::Context& app) {
    app::CliParser cli{app.argc(), app.argv()};
    cli.defineArg<u32>("count");
    cli.parse();
    ...
}

Why Context is a separate, non-template base

The State can’t take Application<S>&: the concept constraining S would have to name Application<S>, which is itself constrained by the concept. So everything that isn’t State-specific lives in app::Context, and the State, workers and helper functions (a fly camera, a worker’s loop) take Context&. None of them need to be templates. Application<S> adds only the std::optional<S> and run(); its constructor is the only way to build a Context.

Public API

template <AppState S>
class Application : public Context {
    explicit Application(Config config, int argc = 0, char** argv = nullptr);
    void run();   // blocks until the window closes
};

class Context {
    struct Config {
        int width = 1280;
        int height = 720;
        const char* title = "GameEngine";
        bool resizable = true;   // false: fixed at width x height (X11)
    };

    void quit();                       // the current frame still finishes
    InputState& input();
    DebugUI& debugUI();                // valid from the State's constructor on
    int argc() const;  char** argv() const;
    int width() const; int height() const;   // framebuffer pixels
    bool isCursorCaptured() const;
    void setCursorCaptured(bool);
    void toggleCursorCapture();

    template <typename F, typename... Args>
    void addWorker(F&& work, Args&&... args);   // work: void(Context&, UserData&)
    bool workerShouldStop() const;
};

Worth knowing

  • One render thread. sokol_app owns the loop; the State’s constructor, frame() and destructor all run on the thread that called run(). A Worker must never call sg_*.
  • Register workers from the State’s constructor. They start once it returns; on shutdown workerShouldStop() goes true and they are joined before ~S(), so a worker’s CUDA teardown finishes while Vulkan is still up.
  • addWorker infers UserData from the work callable’s second parameter (detail::WorkerCallableTraits); args... construct it.
  • The State lives inside the Application, so its address is stable for the whole run — handing this to a worker is safe.
  • The window opens before the State is built, so a fatal command-line error (a missing --model) shows up after the window appears.
  • Fixed-size windows. sokol_app has no “not resizable” option, so with Config::resizable = false the Context sets the X11 window’s minimum and maximum size both to width×height (XSetWMNormalHints, keeping sokol’s own hints) and resizes it back to that size, at the start of init. These are hints the window manager may ignore. On Hyprland (XWayland) the window floats at exactly that size instead of being tiled, but an explicit X11 resize request (XResizeWindow from another client) still resizes it. Other platforms ignore the flag.
  • Input events are translated into InputState before frame(); ImGui-consumed events never reach it. The State has no raw-event hook yet.
