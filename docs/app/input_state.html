app::InputState

Thread-safe keyboard/mouse state: down/pressed/released per key or button, mouse position/delta, scroll delta.

Role

GLFW delivers input via callbacks fired during glfwPollEvents(), which has to run on the main thread. Workers (the render loop, any future game-logic worker) run on separate threads and need to read "what's the input right now" without racing the callback thread, and need "pressed" (this frame only) and "held" (every frame it's down) to actually mean different things.

Depends on / depended on by

Depends only on Eigen and the standard library (<shared_mutex>). Owned by app::Application; written to by app::Window's GLFW callback trampolines; read by whatever worker drives the game loop (currently sandbox/model_test/main.cpp's renderLoop, which also uses it for the Escape/cursor-capture toggle via app::Application::toggleCursorCapture()).

Public API

class InputState {
    // Called from the GLFW callback thread (main thread) only.
    void handleKey(int key, int action);
    void handleMouseButton(int button, int action);
    void handleCursorPos(f64 x, f64 y);
    void handleScroll(f64 x_offset, f64 y_offset);

    // Call once per frame from whichever worker drives the game loop.
    void beginFrame();

    bool isKeyDown(int key) const;
    bool isKeyPressed(int key) const;
    bool isKeyReleased(int key) const;
    bool isMouseButtonDown(int button) const;
    bool isMouseButtonPressed(int button) const;
    bool isMouseButtonReleased(int button) const;
    Eigen::Vector2f mousePosition() const;
    Eigen::Vector2f mouseDelta() const;
    Eigen::Vector2f scrollDelta() const;
};

Keys/buttons are raw GLFW int codes (GLFW_KEY_W, GLFW_MOUSE_BUTTON_LEFT, ...), not a wrapped engine-native enum — a deliberate call, not an oversight: GLFW's codes are already a stable, widely-known standard, and hand-mapping every key into a new enum is ceremony nobody asked for. The cost is that a caller needs #include <GLFW/glfw3.h> for the constants, a small crack in "only Window touches GLFW."

Reader-writer lock, not a plain mutex

Query methods take a std::shared_lock — any number of worker threads can read concurrently. Anything that mutates state (handle*() and beginFrame()) takes a std::unique_lock — exclusive, since both the callback thread and the frame-boundary call write into the same arrays.

Three tiers of state

  1. Live "is it down" state — one bool array per key/button, written directly by GLFW callbacks, read directly by isKeyDown()/ isMouseButtonDown(). No snapshot involved: "is this down right now" has an unambiguous answer at any instant, it doesn't need a reference point.
  2. Live accumulators for edge events — separate "pressed since last frame" / "released since last frame" arrays, set the instant a GLFW_PRESS/GLFW_RELEASE callback fires, plus a continuously-summed scroll-delta accumulator. Because these record the event as it happens rather than sampling state later, a key that's pressed and released entirely between two beginFrame() calls still gets seen — a naive "diff two point-in-time samples" approach would miss it.
  3. Snapshot state — what isKeyPressed(), isKeyReleased(), mouseDelta(), and scrollDelta() actually read. Only beginFrame() writes it: copies each accumulator into its snapshot and clears the accumulator, and computes mouse delta as current_live_position - position_at_last_beginFrame().

The snapshot exists to give "pressed" one well-defined meaning for the whole frame — not primarily about lag or thread races (the mutex already handles those). Without it, "was Space just pressed" would mean "since whenever this particular caller last asked," which falls apart the moment more than one system reads input in the same frame: different callers, or the same caller reading twice, could get different answers depending on exactly when they ask. beginFrame() gives every reader for the rest of that frame the same stable answer.

Worth knowing

  • who calls beginFrame(): whichever worker acts as the game/render loop, once per iteration — not baked into Application::run(), since that loop just polls GLFW on the main thread at whatever cadence the OS delivers events, not the same cadence as a render/game frame.
  • Bounds-checked against out-of-range key/button indices (GLFW can report GLFW_KEY_UNKNOWN, -1) — out-of-range calls are silently ignored rather than indexing off the end of an array.
  • Escape/cursor-capture toggling lives in main.cpp's renderLoop, not Application — it uses the snapshot-based isKeyPressed() since that loop already calls beginFrame() every iteration; see Application.
