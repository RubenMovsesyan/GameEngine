gpu::Swapchain

Wraps VkSwapchainKHR + its per-image sync primitives. Takes a bare VkSurfaceKHR, so it never learns what a window is.

Role

Builds/rebuilds the swapchain against a surface and a wanted extent, hands out its images as NVRHI textures, and manages the acquire/present semaphore pools. That's the whole job — presentation mechanics, nothing about what gets drawn.

Depends on / depended on by

Built from a gpu::Device + a VkSurfaceKHR (owned by app::Application). graphics::Renderer drives it every frame via acquire()/present().

Public API

class Swapchain {
    Swapchain(const Device&, VkSurfaceKHR, VkExtent2D want);

    struct Acquired {
        u32 image_index = 0;
        bool ok = false; // false => out of date, recreate and skip the frame
    };

    [[nodiscard]] Acquired acquire();
    [[nodiscard]] bool present(u32 image_index);
    void recreate(VkExtent2D want);

    nvrhi::TextureHandle texture(u32 i) const;
    u32 imageCount() const;
    VkExtent2D extent() const;
    VkFormat format() const;

    VkSemaphore imageAvailable() const;             // valid until the next acquire()
    VkSemaphore renderFinished(u32 image_index) const;
};

Worth knowing

  • Format is fixed: VK_FORMAT_B8G8R8A8_UNORM / VK_COLOR_SPACE_SRGB_NONLINEAR_KHR. No HDR/format negotiation.
  • Image usage includes TRANSFER_DST alongside COLOR_ATTACHMENT — required because clearTextureFloat outside a render pass lowers to vkCmdClearColorImage, which needs it.
  • image_available semaphores are keyed by frame (which image you'll get isn't known until acquire() returns); render_finished is keyed by image index, since that's what present() waits on for that specific image. Different rings, different keys, on purpose.
  • Image count can change across a recreate() (rare, but the spec allows it), so semaphore pools get rebuilt every time rather than assuming the old sizing holds.
