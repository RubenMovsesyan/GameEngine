Module

gpu

Everything needed to talk to a Vulkan device: instance, physical-device and queue selection, command submission, frame synchronization, swapchain, and VMA-backed buffers. It knows nothing about windows, rendering, shaders, or pipelines.

The shape of the API

gpu/ is a library of RAII value types, not a framework. That distinction drives every design choice here, so it is worth stating precisely:

A framework would…gpu/ instead…
define an abstract Pipeline/Pass base you subclass, and call your virtuals each frame. hands you a vk::raii::CommandBuffer&. You record whatever you like onto it. There are no virtual functions in the module.
own a global get_core() singleton everyone reaches into. has you construct Instance and Device yourself and pass them by reference. No singleton, no shared_ptr graph.
wrap every Vulkan handle in a bespoke class. wraps only what Vulkan-Hpp doesn't already: there is no gpu::CommandBuffer, because vk::raii::CommandBuffer is that type.

Direction of control is one-way: graphics/ calls into gpu/, and gpu/ never calls back. That is what lets a physics module use the same device without the renderer existing.

Instance

Instance owns the vk::raii::Context, the VkInstance, and an optional debug messenger. Its config is the entire windowing seam on this side: 

struct InstanceConfig {
    const char* app_name = "GameEngine";
    u32 api_version = vk::ApiVersion14;
    // Handed through from the windowing layer. The entire window seam on this side.
    std::span<const char* const> required_extensions{};
    bool validation = true;
};

std::span<const char* const> maps exactly onto GLFW's const char** plus count — no copy, no allocation, and critically, no GLFW type in the signature. gpu/ sees an array of strings and nothing more.

Validation

Validation is requested by default but never assumed. If the layer isn't installed the constructor warns and continues rather than dying: 

const bool validation = cfg.validation
    && hasLayer(m_context.enumerateInstanceLayerProperties(), VALIDATION_LAYER);
if (cfg.validation && !validation) {
    RLOG(LL_WARN, "%s not available, continuing without validation", VALIDATION_LAYER);
}

The messenger routes the layer's output into rlog and always returns vk::False, so a validation error is reported but never aborts the call that triggered it: 

VKAPI_ATTR vk::Bool32 VKAPI_CALL debugCallback(
    vk::DebugUtilsMessageSeverityFlagBitsEXT severity,
    vk::DebugUtilsMessageTypeFlagsEXT,
    const vk::DebugUtilsMessengerCallbackDataEXT* data,
    void*
) {
    if (severity == vk::DebugUtilsMessageSeverityFlagBitsEXT::eError) {
        RLOG(LL_ERROR, "[vk] %s", data->pMessage);
    } else {
        RLOG(LL_WARN, "[vk] %s", data->pMessage);
    }
    return vk::False; // never abort the offending call
}
Why the vk:: parameter types

The obvious version of this callback takes the C types (VkDebugUtilsMessageSeverityFlagBitsEXT, …), which is what every tutorial shows. Vulkan-Hpp's pfnUserCallback field is typed with the C++ enums, so the C signature doesn't convert and you need a function-pointer reinterpret_cast. Writing the callback with vk:: types instead makes the cast unnecessary.

Turning validation errors into hard stops

During bring-up it is often better to die on the first validation error than to scroll back through a log. Change one word in gpu/src/instance.cpp: 

RLOG(LL_FATAL, "[vk] %s", data->pMessage);   // was LL_ERROR

LL_FATAL calls exit(404), so you get an immediate, attachable stop.

Device

Device picks a physical device, selects queue families, creates the logical device, retrieves the queues, and creates the VMA allocator.

Queue family selection

This is where the previous attempt had a real bug, so the helper is written to make that bug impossible: 

// First match, then stop. No silent fallback to family 0.
std::optional<u32> pickFamily(
    const std::vector<vk::QueueFamilyProperties>& props,
    vk::QueueFlags required,
    vk::QueueFlags forbidden
) {
    for (u32 i = 0; i < props.size(); i++) {
        const vk::QueueFlags flags = props[i].queueFlags;
        if ((flags & required) == required && !(flags & forbidden)) {
            return i;
        }
    }
    return std::nullopt;
}
The bug this replaces

ShaderPlayground's selection loop had no break, so it kept the last matching family rather than the first. On a typical discrete GPU — where family 0 is graphics|compute|transfer and later families are specialised — that silently landed on the wrong family. Both indices also defaulted to 0 with no failure path, so "no suitable family" was indistinguishable from "family 0".

The forbidden parameter is what expresses "dedicated". Asking for compute while forbidding graphics finds an async-compute family if the hardware has one, and falls back to the graphics family if it doesn't: 

QueueFamilies families{
    .graphics = *graphics,
    .compute  = pickFamily(props, Q::eCompute,  Q::eGraphics).value_or(*graphics),
    .transfer = pickFamily(props, Q::eTransfer, Q::eGraphics | Q::eCompute).value_or(*graphics),
};

Present support is checked only when a surface was supplied, and prefers the graphics family so submission and presentation share a queue where possible: 

if (surface) {
    // Prefer the graphics family so submission and present share a queue.
    if (gpu.getSurfaceSupportKHR(*graphics, surface)) {
        families.present = *graphics;
        families.has_present = true;
    } else {
        for (u32 i = 0; i < props.size(); i++) {
            if (gpu.getSurfaceSupportKHR(i, surface)) {
                families.present = i;
                families.has_present = true;
                break;
            }
        }
    }
    if (!families.has_present) {
        return std::nullopt;   // this device cannot present to this surface
    }
}

Queues alias freely when their families are equal — vk::raii::Queue destruction is a no-op, so holding the same underlying queue in two members is safe.

Required features

A device that can't do dynamic rendering and synchronization2 is skipped, not worked around: 

bool supportsRequiredFeatures(const vk::raii::PhysicalDevice& gpu) {
    const auto chain = gpu.getFeatures2<vk::PhysicalDeviceFeatures2,
                                        vk::PhysicalDeviceVulkan13Features>();
    const auto& vk13 = chain.get<vk::PhysicalDeviceVulkan13Features>();
    return vk13.dynamicRendering && vk13.synchronization2;
}

They are then enabled through a structure chain at device creation:

const vk::StructureChain<vk::DeviceCreateInfo, vk::PhysicalDeviceVulkan13Features> chain{
    vk::DeviceCreateInfo{ /* queues, extensions */ },
    vk::PhysicalDeviceVulkan13Features{
        .synchronization2 = vk::True,
        .dynamicRendering = vk::True,
    },
};
m_device = vk::raii::Device{m_physical, chain.get<vk::DeviceCreateInfo>()};

Selection prefers a discrete GPU and stops as soon as it finds one. If no candidate survives, RLOG(LL_FATAL, …) ends the process — there is no error-propagation plumbing through constructors.

VMA, and the one ordering rule

VMA is a C library that wants raw handles, and vk::raii types convert with a dereference plus a cast. The subtle part is telling VMA how to find its function pointers: 

VmaVulkanFunctions functions{
    .vkGetInstanceProcAddr = instance->getDispatcher()->vkGetInstanceProcAddr,
    .vkGetDeviceProcAddr   = m_device.getDispatcher()->vkGetDeviceProcAddr,
};
const VmaAllocatorCreateInfo allocator_info{
    .physicalDevice   = static_cast<VkPhysicalDevice>(*m_physical),
    .device           = static_cast<VkDevice>(*m_device),
    .pVulkanFunctions = &functions,
    .instance         = static_cast<VkInstance>(instance.handle()),
    .vulkanApiVersion = VK_API_VERSION_1_4,
};

Each vk::raii object carries its own dispatch table rather than using a global one, so those two bootstrap pointers come from the dispatchers themselves. The build sets -DVMA_STATIC_VULKAN_FUNCTIONS=0 -DVMA_DYNAMIC_VULKAN_FUNCTIONS=1 so VMA resolves the rest through them instead of the loader's exported symbols.

Do not reorder Device's members

vmaDestroyAllocator must run before vkDestroyDevice. Nothing enforces that except member declaration order — members are destroyed in reverse, so the allocator is declared last: 

vk::raii::Device m_device{nullptr};
// ...
// Declared last so it is destroyed first: vmaDestroyAllocator must run before
// vkDestroyDevice. Do not reorder.
std::unique_ptr<VmaAllocator_T, void (*)(VmaAllocator_T*)> m_allocator{nullptr, nullptr};

The check that this held is the validation layer's object-leak report at vkDestroyInstance. A clean exit with zero leak messages is the proof; treat any leak message as a hard failure.

The unique_ptr deleter is a plain function pointer, which is why VmaAllocator_T can stay an incomplete forward declaration in the header and vk_mem_alloc.h — roughly 750 KB — never lands in a consumer's translation unit.

Commands and submission

There is no command-buffer class. Recording is done directly on vk::raii::CommandBuffer, and gpu/ adds only the two things worth not retyping: a barrier helper and one submission path. 

// The single submission path for graphics and compute.
struct SubmitInfo {
    const vk::raii::CommandBuffer* cmd = nullptr;
    vk::Semaphore wait{};
    vk::PipelineStageFlags2 wait_stage = vk::PipelineStageFlagBits2::eAllCommands;
    vk::Semaphore signal{};
    vk::PipelineStageFlags2 signal_stage = vk::PipelineStageFlagBits2::eAllCommands;
    vk::Fence fence{}; // reset here, immediately before submitting
};

void submit(const Device&, const vk::raii::Queue&, const SubmitInfo&);

Every wait and signal is optional, so the same function serves a graphics frame (wait on acquire, signal render-finished) and a fire-and-forget compute dispatch (neither). The counts are derived from whether the handles are non-null: 

queue.submit2(vk::SubmitInfo2{
    .waitSemaphoreInfoCount   = info.wait ? 1u : 0u,
    .pWaitSemaphoreInfos      = &wait,
    .commandBufferInfoCount   = 1,
    .pCommandBufferInfos      = &cmd,
    .signalSemaphoreInfoCount = info.signal ? 1u : 0u,
    .pSignalSemaphoreInfos    = &signal,
}, info.fence);

submit takes the Device for exactly one reason: to reset the fence itself. That placement is load-bearing and is explained in Synchronization.

Buffers

Buffer is the module's only hand-written destructor, because VMA is a C API with no RAII of its own. 

gpu::Buffer buffer{device, 64, vk::BufferUsageFlagBits::eStorageBuffer, /*host_visible=*/true};
std::memset(buffer.mapped(), 0xAB, 64);

When host_visible is set, VMA maps the allocation persistently and mapped() is non-null for the buffer's lifetime — there is no map/unmap dance. Otherwise mapped() is nullptr and the memory is device-local.

Move assignment is a swap, so the moved-from object's destructor releases the old resources:

// Swap, so other's destructor releases whatever we were holding.
Buffer& Buffer::operator=(Buffer&& other) noexcept {
    std::swap(m_allocator, other.m_allocator);
    std::swap(m_allocation, other.m_allocation);
    std::swap(m_buffer, other.m_buffer);
    std::swap(m_size, other.m_size);
    std::swap(m_mapped, other.m_mapped);
    return *this;
}
No staging path yet

Uploading to a device-local buffer needs a staging buffer and a transfer-queue copy. Neither exists — QueueFamilies::transfer is selected but unused. That is deliberate: it arrives with the first vertex buffer that needs it.

Using gpu/ headless

This is the payoff for the whole split, and it is why DeviceConfig::present_surface is a nullable field rather than a constructor requirement. A compute or physics module constructs a device with no surface at all: 

// No window, no graphics/, no swapchain.
const gpu::Instance instance{{.validation = true}};
const gpu::Device device{instance};          // present_surface stays null

gpu::Buffer out{device, 1024, vk::BufferUsageFlagBits::eStorageBuffer, true};
gpu::FrameRing frames{device, device.families().compute, 1};

const auto frame = frames.begin();
frame.cmd.begin({.flags = vk::CommandBufferUsageFlagBits::eOneTimeSubmit});
// ... bind a compute pipeline, cmd.dispatch(...) ...
frame.cmd.end();

gpu::submit(device, device.computeQueue(), {.cmd = &frame.cmd, .fence = frame.fence});

With no surface, Device selects no present queue and doesn't request VK_KHR_swapchain. The same FrameRing and the same submit that the renderer uses work unchanged — which is exactly the duplication the previous attempt fell into and this one avoids.

Rules and traps

Never call a method on a bare handle

Call methods on vk::raii:: types only. A bare vk::Device, vk::CommandBuffer or vk::Queue routes through a second, static dispatcher — a separate and invisible dispatch path. Bare handles are fine to pass around; they are not fine to call on. That is why imageBarrier and SubmitInfo::cmd take const vk::raii::CommandBuffer& rather than the plain handle.

-DVULKAN_HPP_NO_CONSTRUCTORS is required

Without it, vk:: structs have constructors, are therefore not aggregates, and every designated initializer in this module fails to compile. It is set in build.c's cxxStep() so all steps share it — a mismatch between steps would be an ODR violation, since the flag changes the class definitions themselves.

Errors

Setup failures we detect ourselves are RLOG(LL_FATAL, …), which exits. Vulkan errors surface as vk::SystemError exceptions and are caught once, in main. Recoverable per-frame conditions — an out-of-date swapchain — are return values and never exceptions at the API boundary.
