app::Application

Owns the window, the GPU device and swapchain, and the workers. The runtime shell everything else runs inside.

Role

Constructs the whole GPU stack in one initializer list (window → instance → surface → device → swapchain, in that order, since each depends on the previous) and runs registered workers on their own threads while polling window events on the main thread. Rendering itself lives entirely off Application — graphics::Renderer owns its own present loop, run from a worker.

Depends on / depended on by

Depends on app::Window/Worker, gpu::Instance/Device/Swapchain. Constructed directly by main(); every worker function receives a reference to it.

Public API

class Application {
    Application();

    void run();
    std::atomic<bool> running = false;

    gpu::Device& device();
    gpu::Swapchain& swapchain();
    InputState& input();
    bool isCursorCaptured() const;   // forwards to Window::isCursorCaptured()
    void toggleCursorCapture();      // forwards to Window::toggleCursorCapture()

    template <typename F, typename... Args>
    void addWorker(F&& work, Args&&... args);   // UserData inferred from work's 2nd parameter
};

Worth knowing

  • addWorker infers UserData from the work callable's second parameter type (via detail::WorkerCallableTraits, see Worker) — args... construct that UserData, so you never spell the type out explicitly.
  • running is public and atomic on purpose — worker loops read it directly (while (app.running.load())) without needing an accessor.
  • The private OwnedSurface nested class exists purely for destruction ordering: it must outlive the swapchain built from it but not outlive the instance it was created from — member declaration order encodes that (C++ destroys members in reverse declaration order).
  • Destructor joins every worker before vkDeviceWaitIdle — no GPU resource gets torn down while a worker might still be using it.
  • Application only exposes cursor-capture mechanism (isCursorCaptured()/toggleCursorCapture(), both thin forwards to Window) — deciding when to toggle (e.g. on Escape) is left to whoever drives the game loop (sandbox/model_test/main.cpp's renderLoop), since that's also the thing calling InputState::beginFrame() and can use the snapshot-based isKeyPressed() correctly. run()'s own poll loop doesn't touch input policy at all.
