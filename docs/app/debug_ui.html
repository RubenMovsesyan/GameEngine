app::DebugUI

Dear ImGui, wired to the window rather than to any particular Renderer target — a checkbox panel for engine-wide debug toggles.

Role

A thin wrapper over sokol_imgui.h (vendored at external/sokol/util/sokol_imgui.h), which does the actual ImGui setup, rendering, and event translation against Dear ImGui itself (vendored at external/imgui, pinned to v1.92.9b — a tagged release, not master, since ImGui's API shifts more than the other vendored dependencies here). DebugUI adds nothing beyond a visibility flag and the "no-op while hidden" contract described below.

Owned by Application, not Renderer

Renderer is a "draw a scene from a camera into some target" object — it already renders several offscreen targets internally (G-buffer, HDR, LDR) before ever touching the swapchain, and nothing stops a second camera from targeting an offscreen texture (a minimap, a security-camera view) later. A debug panel toggling engine-wide features is a window/session concept, not tied to any one render target, so app::Application owns one DebugUI for the life of the window — exactly like it already owns one InputState — independent of however many Renderers or cameras exist.

This runs into one real constraint: ImGui still has to render into the actual swapchain image, and the only point in the frame that touches the swapchain is inside Renderer::endFrame()'s FXAA pass. Rather than have Renderer learn about DebugUI or ImGui at all, endFrame() takes one new parameter — an opaque std::function<void()> — invoked at the same point DebugDraw::render() already runs, right before sg_end_pass(). Renderer never names DebugUI or ImGui; the sandbox is what wires "the app's debug panel" into "the renderer's last swapchain-writing point," the same way it already wires renderer.debugDraw() calls into the frame.

Off by default, and a true no-op when hidden

setVisible(false) is the constructed state. draw() starts with if (!m_visible) return; before touching simgui_new_frame, before invoking the caller's panels callback, before simgui_render() — so no ImGui:: call the caller makes inside panels ever runs while the panel is hidden, and no ImGui frame is even constructed. Same guarantee graphics::primitives::pass::DebugDraw already gives.

handleEvent() is the one method that does not gate on visibility — it always forwards to simgui_handle_event(). With nothing drawn, ImGui has nothing to hover or focus, so it naturally never reports an event as consumed while hidden; always feeding keeps its internal input state (deltas, hover) correct for the moment the panel is shown again, rather than resyncing from a blank state on every open.

Public API

class DebugUI {
    DebugUI();  // simgui_setup() -- unconditional, one-time cost
    ~DebugUI(); // simgui_shutdown()

    void setVisible(bool);
    bool isVisible() const;

    bool handleEvent(const sapp_event&);  // true if ImGui consumed it

    void draw(int width, int height, double delta_time, float dpi_scale,
              const std::function<void()>& panels);
};

Depends on / depended on by

Depends on the vendored sokol_imgui.h and, transitively, real imgui.h — no dependency on graphics/ or any GPU resource wrapper. Application owns the only instance (std::optional<DebugUI>, constructed once sg_setup() has run — see initCallback), feeds it every sapp_event from eventCallback before InputState gets a look, and exposes it via Application::debugUI(). Game code (the sandbox) reaches it through that accessor to register panel content and to wire it into Renderer::endFrame's overlay parameter each frame.

Event routing

Application::eventCallback calls debugUI().handleEvent(event) first; if it returns true, the event stops there and never reaches InputState. This is why clicking a checkbox doesn't also register as a mouse click for gameplay — but it also means an open panel silently swallows any input the game might otherwise have wanted, so the sandbox force-uncaptures the cursor when the panel opens (flyCamera already gates mouse-look on isCursorCaptured(), so nothing else is needed to stop the camera fighting the panel).

What isn't here yet

  • Keyboard capture. Nothing checks ImGui::GetIO().WantCaptureKeyboard, so WASD still moves the camera while the panel is focused. Not a problem yet — today's panel is checkboxes and a slider, no text fields to steal keystrokes from. Worth wiring if a text input is ever added.
  • Panel content beyond the three existing debug toggles (shadow-map debug, cascade layer, DebugDraw enable). Extending it is adding another ImGui::Checkbox/SliderInt/etc. call inside the sandbox's panels lambda — no engine-side change needed.
  • Docking, viewports, the demo window. None vendored or wired up; the pinned tag (v1.92.9b) is deliberately the non-docking release.
