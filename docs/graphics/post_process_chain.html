graphics::PostProcessChain

An ordered, extensible chain of full-screen shader passes run after the lighting pass. The last pass writes the swapchain.

Role

Each registered pass is one fragment shader: reads one input texture, writes one output. The chain manages ping-ponging between two HDR scratch targets for you — you never touch that plumbing directly, just addPass() and (optionally) setPushConstants() per frame. Renderer registers two passes at construction: tonemap.frag (exposure multiply + an ACES approximation curve, fused since they're always used together), then fxaa.frag (a minimal FXAA edge-blur on the tonemapped LDR image, toggled via Renderer::setFxaaEnabled()).

Depends on / depended on by

Depends on gpu::Device, Surface. Owned and driven by Renderer, which registers the default tonemap pass at construction.

Public API

class PostProcessChain {
    explicit PostProcessChain(const gpu::Device&);

    u32 addPass(const u32* fragment_spirv, usize word_count, usize push_constant_size);
    void rebuild(VkExtent2D extent, nvrhi::Format swapchain_format);
    void setPushConstants(u32 pass_index, const void* data, usize size);
    void run(nvrhi::ICommandList*, nvrhi::ITexture* hdr_input, const Surface& swapchain_target);
};

Adding your own pass

  1. Write a .frag under src/graphics/shaders/. Same shape as tonemap.frag: sample tInput@binding 0 + sLinear@binding 1, read vUv, write outColor.
  2. Add its filename to build.cpp's shader-compile list.
  3. Wherever the chain is built (currently Renderer's constructor), #include the generated header and call addPass(), capturing the returned index if you'll need setPushConstants() later.
  4. Call rebuild() again — pipeline creation needs the complete, final pass list, since only the last pass targets the swapchain's LDR format and every other pass targets the HDR scratch format.

Extension is compile-time only, matching every other shader in this engine — there's no runtime shader loading or hot-reload. Registration order matters: passes run in the order registered, and whichever runs last is the one that writes the swapchain.

Worth knowing

  • Only two HDR scratch Surfaces exist regardless of chain length — passes alternate between them, and the last pass writes the real swapchain target instead of a scratch buffer.
  • Every pass shares one binding layout (input texture @0, sampler @1); push constants get their own separate layout per pass, only created if that pass's push_constant_size > 0.
  • Strictly one-texture-in/one-texture-out per pass. Multi-input or multi-target effects (bloom, SSAO) don't fit this shape — they'd need downsample/upsample chains with several intermediate targets, which this class doesn't provide.
  • Only the first pass sees the HDR target the right way up. NVRHI's Vulkan viewport is Y-flipped for every draw. tonemap.frag (pass 0) samples with that flip and thereby un-flips the image; every pass after it re-introduces the flip and must cancel it by sampling with an inverted Y (fxaa.frag uses vec2(vUv.x, 1.0 - vUv.y)). Any custom pass added after the first one needs the same one-line inversion.
