graphics

The renderer, and the only module in the engine that knows a display exists. It owns the window, creates the surface, and drives gpu/ to produce a frame. Today that frame is a clear — but the structure around it is the real deliverable.

The seam with gpu/

gpu/ must never include GLFW. Two functions carry everything across that line, and both live in graphics/src/window.cpp — the only translation unit in the entire project that includes <GLFW/glfw3.h>.

1. Instance extensions

std::span<const char* const> requiredInstanceExtensions() {
    if (glfwInit() != GLFW_TRUE) {
        RLOG(LL_FATAL, "glfwInit failed");
    }
    u32 count = 0;
    const char** extensions = glfwGetRequiredInstanceExtensions(&count);
    if (extensions == nullptr) {
        RLOG(LL_FATAL, "Vulkan is not available to GLFW");
    }
    return {extensions, count};
}

GLFW returns a static const char** plus a count. A std::span<const char* const> is exactly that pair, so this is a view with no copy and no allocation. On the gpu/ side the type is just a span of strings — there is no GLFW type anywhere in the signature.

2. The surface

vk::raii::SurfaceKHR Window::createSurface(const gpu::Instance& instance) const {
    VkSurfaceKHR surface = VK_NULL_HANDLE;
    const VkResult result = glfwCreateWindowSurface(
        static_cast<VkInstance>(instance.handle()), m_window, nullptr, &surface);
    if (result != VK_SUCCESS) {
        RLOG(LL_FATAL, "glfwCreateWindowSurface failed: %d", result);
    }
    return instance.adoptSurface(surface);
}

GLFW hands back a raw VkSurfaceKHR, and gpu::Instance::adoptSurface wraps it so vk::raii owns its destruction from that point. The returned vk::raii::SurfaceKHR is owned by main, and a plain vk::SurfaceKHR is what gets passed into gpu::DeviceConfig and gpu::Swapchain.

Why this is the whole seam

An array of strings and one opaque handle. That is the total surface area between "we have a window" and "we have a GPU". Everything else in gpu/ is reachable from a compute-only program that never creates either.

Window

Window is a thin RAII wrapper. Note the forward declaration in the header — struct GLFWwindow; — which keeps the GLFW header out of every consumer: 

struct GLFWwindow;

namespace ge::gfx {

std::span<const char* const> requiredInstanceExtensions();

class Window {
public:
    Window(int width, int height, const char* title);
    ~Window();

    Window(Window&&) = delete;
    Window& operator=(Window&&) = delete;

    vk::raii::SurfaceKHR createSurface(const gpu::Instance&) const;

    bool shouldClose() const;
    vk::Extent2D framebufferExtent() const;
    static void poll();
    static void waitEvents();

private:
    GLFWwindow* m_window = nullptr;
};

} // namespace ge::gfx

Move is deleted rather than implemented. Nothing needs to move a window, and deleting it is one line where a correct move constructor would be several. glfwWindowHint(GLFW_CLIENT_API, GLFW_NO_API) in the constructor is what stops GLFW creating an OpenGL context we would never use.

framebufferExtent() returns the framebuffer size, not the window size. On a HiDPI or scaled display these differ, and the swapchain wants the framebuffer one.

Ownership order

There is no engine object and no lifetime manager. Destruction order is correct because declaration order is correct — members and locals are destroyed in reverse: 

void run() {
    ge::gfx::Window window{1280, 720, "sandbox"};

    const gpu::Instance instance{{.required_extensions = ge::gfx::requiredInstanceExtensions()}};
    const vk::raii::SurfaceKHR surface = window.createSurface(instance);
    const gpu::Device device{instance, {.present_surface = *surface}};

    // Declared last, so it is destroyed before the device.
    ge::gfx::Renderer renderer{device, *surface, window.framebufferExtent()};

    // ... loop ...
    device.waitIdle();
}
DeclaredObjectDestroyed
1stWindowlast — glfwTerminate after all Vulkan objects are gone
2ndInstance4th
3rdSurfaceKHR3rd — before the instance that owns it
4thDevice2nd
5thRenderer1st — swapchain and frame ring die before the device

device.waitIdle() before returning is what guarantees no command buffer or semaphore is still in use when the renderer's destructor runs.

The check that this is right

Close the window normally and look for validation output at vkDestroyInstance. The layer reports every object that was never destroyed. Zero leak messages is the proof; anything else is a hard failure, not a warning.

A frame, step by step

Renderer::drawFrame is the whole render loop. Walking it in order shows how the gpu/ pieces compose.

0 — bail out or rebuild

if (extent.width == 0 || extent.height == 0) {
    return; // minimised
}
if (m_needs_recreate || extent != m_swapchain.extent()) {
    m_device->waitIdle();
    m_swapchain.recreate(extent);
    m_needs_recreate = false;
}

1 — take a frame slot

const gpu::FrameRing::Frame frame = m_frames.begin();

Blocks until this slot's previous work is done. The fence is not reset here — see the fence reset.

2 — acquire an image

const auto acquired = m_swapchain.acquire(frame.semaphore);
if (!acquired.ok) {
    m_needs_recreate = true; // fence is still signalled, so the slot stays usable
    return;
}

The acquire semaphore comes from the frame slot; the image index comes back from the swapchain. This is the exact point where the two indices diverge.

3 — record

frame.cmd.begin({.flags = vk::CommandBufferUsageFlagBits::eOneTimeSubmit});

gpu::imageBarrier(frame.cmd, image,
    vk::ImageLayout::eUndefined, vk::ImageLayout::eColorAttachmentOptimal, /* ... */);

const vk::RenderingAttachmentInfo color{
    .imageView   = m_swapchain.view(acquired.image_index),
    .imageLayout = vk::ImageLayout::eColorAttachmentOptimal,
    .loadOp      = vk::AttachmentLoadOp::eClear,
    .storeOp     = vk::AttachmentStoreOp::eStore,
    .clearValue  = clear,
};
// Nothing is drawn yet: the loadOp is the frame.
frame.cmd.beginRendering(vk::RenderingInfo{
    .renderArea = {{0, 0}, m_swapchain.extent()},
    .layerCount = 1,
    .colorAttachmentCount = 1,
    .pColorAttachments = &color,
});
frame.cmd.endRendering();

gpu::imageBarrier(frame.cmd, image,
    vk::ImageLayout::eColorAttachmentOptimal, vk::ImageLayout::ePresentSrcKHR, /* ... */);

frame.cmd.end();

This uses dynamic rendering — no VkRenderPass, no VkFramebuffer. Those would be roughly 120 lines of attachment descriptions, subpass dependencies and per-image framebuffers that all have to be torn down and rebuilt on every resize. Here it is one stack struct and a begin/end pair.

Draw commands would go between beginRendering and endRendering. Right now there are none, and the eClear load op is the entire frame.

4 — submit and present

gpu::submit(*m_device, m_device->graphicsQueue(), {
    .cmd        = &frame.cmd,
    .wait       = frame.semaphore,                                  // per frame slot
    .wait_stage = vk::PipelineStageFlagBits2::eColorAttachmentOutput,
    .signal     = m_swapchain.renderFinished(acquired.image_index), // per image
    .fence      = frame.fence,
});

if (!m_swapchain.present(m_device->presentQueue(), acquired.image_index)) {
    m_needs_recreate = true;
}
m_frames.advance();

Those two adjacent lines are the clearest statement of the indexing rule: the wait semaphore is indexed by frame slot, the signal semaphore by image index.

Waiting at eColorAttachmentOutput rather than at the top of the pipe means the GPU can start any earlier stages before the image is actually available.

Why those two barriers

First barrierSecond barrier
LayouteUndefined → eColorAttachmentOptimaleColorAttachmentOptimal → ePresentSrcKHR
Src stage / accesseTopOfPipe / noneeColorAttachmentOutput / eColorAttachmentWrite
Dst stage / accesseColorAttachmentOutput / eColorAttachmentWriteeBottomOfPipe / none

eUndefined as the old layout is intentional, not laziness. It tells the driver the existing contents may be discarded, which is both true — loadOp = eClear overwrites everything — and cheaper than a transition that preserves them.

The second barrier has no destination access mask. The present engine's visibility is established by the render-finished semaphore, not by this barrier, so specifying one would be redundant.

Verifying the layer is actually watching

"No validation errors" and "validation isn't loaded" look identical. Delete the second barrier and run: the layer must immediately report 

vkQueuePresentKHR(): pPresentInfo images passed to present must be in layout
VK_IMAGE_LAYOUT_PRESENT_SRC_KHR ... but VkImage ... is in VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL.

If it stays silent, validation is not running and every clean run so far proved nothing. Restore the barrier and confirm the message goes away.

Extending it

There is no base class to subclass and no virtual to override. The extension point is that frame.cmd is a vk::raii::CommandBuffer& and you record whatever you want onto it between beginRendering and endRendering.

Concretely, to draw a triangle from here:

  1. Compile GLSL to SPIR-V in build.c with a glslc prebuild command, embedding the result as a header.
  2. Create a vk::raii::Pipeline with vk::PipelineRenderingCreateInfo in its chain — dynamic rendering pipelines declare their attachment formats instead of taking a render pass.
  3. Between the begin/end pair: frame.cmd.bindPipeline(...), setViewport, setScissor, draw(3, 1, 0, 0).

None of that touches gpu/. Pipelines, shaders and descriptor sets are rendering concepts and belong here — putting them in the GPU layer is precisely the mistake described in the overview.

Where a compute pass would go

Not here. A physics or compute module builds its own gpu::FrameRing on device.families().compute and calls gpu::submit on device.computeQueue(). To interleave it with rendering, chain the semaphores: the compute submit signals one, and the graphics submit waits on it. That path uses the same submit the renderer already exercises every frame — no new machinery.
