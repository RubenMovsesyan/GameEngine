graphics::LightManager

Turns a set of Lights into one GPU-readable structured buffer, built explicitly rather than lazily.

Role

Collects non-owning pointers to Lights via add(), then build() packs all of them into a single structured buffer (StructuredBuffer_SRV-shaped) and uploads it once. buffer() and count() are what Renderer::setLights() reads each frame.

Depends on / depended on by

Depends on gpu::Device (for the upload) and graphics::Light. Renderer::setLights(const LightManager&) is the only consumer.

Public API

class LightManager {
    explicit LightManager(const gpu::Device&);

    void add(const Light&);       // non-owning: caller keeps the Light alive
    void build();                 // uploads everything added so far
    nvrhi::IBuffer* buffer() const;
    u32 count() const;
};

Why build() is explicit, not lazy

The first version of this class built its GPU buffer lazily, the first time buffer() was called after a change. That broke in practice: gpu::Device::createBuffer uploads data by opening its own short-lived immediate command list — safe when called before the render loop starts (as Mesh::create does), but Renderer::setLights() is called between beginFrame() and endFrame(), i.e. while Renderer's own command list is already open. The first frame a real light existed, the lazy build tried to open a second immediate command list mid-frame and NVRHI's validation layer rejected it ("two or more immediate command lists cannot be open at the same time"), then cascaded into three more errors from the never-opened command list. Explicit build(), called once after all add()s and safely outside any render-pass command list, sidesteps this entirely.

GPU layout

The private GpuLight struct packs every field into four vec4s — std430-safe by construction (each member naturally 16-byte aligned), no manual padding math. LightType rides in as a plain float in the last component of one of them, since everything else in the struct is already a vec4.

Worth knowing

  • buffer() returns nullptr if nothing was ever added — Renderer has its own placeholder buffer for that case (a StructuredBuffer_SRV binding can't take a null handle).
  • No remove() — not needed yet; add-only.
